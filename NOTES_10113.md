### Django, using Plane's own code

**Models and managers.** A manager is what you query through: `Model.objects.filter(...)`. `Issue.objects` is `SoftDeletionManager` (`db/mixins.py:57-67`): it hides rows with `deleted_at` set. `Issue.all_objects` includes soft-deleted rows. `Issue.issue_objects = IssueManager()` (`db/models/issue.py:92-102, 172`) is stricter: it also excludes triage-state issues, archived issues, issues of archived projects and drafts. Rule of thumb in this codebase: user-facing lists use `issue_objects`; "does this issue exist for permission purposes" checks use `objects`. Managers do **not** check who is asking; nothing in the ORM knows about the request user. Every view must add that filter itself, which is the root of this bug.

**ViewSets.** `BaseViewSet(ModelViewSet)` (`app/views/base.py`) is DRF's class-based "CRUD for one model". You override `list`, `create`, ... The URL file picks which methods are exposed. `self.kwargs` holds the URL parameters; Plane exposes `workspace_slug` and `project_id` properties from them, which permission classes use.

**Permission classes.** A DRF permission class has `has_permission(request, view)` and runs before the handler. Returning `False` gives a 403. `ProjectEntityPermission` (`app/permissions/project.py:135`) is one. Decorators like `@allow_permission([ROLE.ADMIN, ROLE.MEMBER])` (`app/permissions/base.py:19`) do the same thing per method. Neither inspects the *data* the handler later returns; that is the handler's job.

**Serializers.** Convert model instances to JSON and validate input (`IssueRelationSerializer`, `app/serializers/issue.py:412`). `IssueRelationViewSet.list` does not use one; it returns `queryset.values(...)`, which are plain dicts straight from SQL.

**Querysets.** Lazy: nothing hits the DB until iterated (here, when the JSON renderer runs). `filter(a=1, b=2)` ANDs conditions. `Q(...) | Q(...)` builds OR. Double underscores traverse relations and become SQL JOINs: `project__project_projectmember__member=user` joins issue → project → project_members. **Conditions in one `filter()` call share one join; separate `filter()` calls on a multi-valued relation create separate joins** (this is why `_visible_issues_q` says "use within a single `filter()` call", `workspace/user.py:73-74`). `Subquery(...)`/`OuterRef("id")` run an inner query per outer row; see `cycle_id` in `relation.py:145`. `.annotate(...)` adds computed columns. `.values(...)` returns dicts.

**pytest.** Fixtures are functions injected by parameter name. `create_user` → `workspace` (`tests/conftest.py`) build up the data; `session_client` is an `APIClient` with `force_authenticate`. `@pytest.mark.django_db` gives each test a rolled-back transaction. `pytest.ini` runs with `--reuse-db --nomigrations`, so tables come from the models, not migrations.

## 3. The bug

**Is it real? Yes (VERIFIED by a failing test on unmodified code, section 6).**

*Data setup that leaks:* one workspace; Project A and Project B. User **G** is an active GUEST of A only (no `ProjectMember` row in B). Issue **A1** in A was created by G (so a restricted guest may open it). Issue **B1** in B was created by someone else. `IssueRelation(issue=A1, related_issue=B1, relation_type="relates_to")`.

*Why the code returns B1:* every check in front of the queryset is about A and A1 only. `ProjectEntityPermission` passes because G is in A. `issue_in_project` passes because A1 is in A. `issue_hidden_from_guest` passes because G created A1. `issue_relations` then contains the A1↔B1 row (workspace-scoped only), the id list contains B1's id, and `Issue.issue_objects.filter(workspace__slug=slug)` (`relation.py:141`) accepts any issue in the workspace. B1's `name`, `priority`, `sequence_id`, `project_id`, label ids and assignee ids go into the response.

*Evidence:* on base code, `assert str(issue_b1.id) not in _related_ids(response)` fails with `'193b9178-…' in {'193b9178-…'}`.

**It is not specific to guests.** The same query also returns B1 to a *member* of A who is not in B, and to a workspace admin who is a member of A but not B. (VERIFIED: those tests fail on base code too.) The issue title says "guest", but the missing piece is the project-membership check; guests are the case where it matters most because they are the lowest-trust role.

**How sibling code solves it** (the pattern I reused):
- The external API's relation list does it: `visible_issue_ids = Issue.objects.filter(visible_issue_q(request.user))` then restricts relations to those ids (`api/views/issue.py:2583-2595`, commit `3a932da1b`, tests in `tests/contract/api/test_external_api_guest_issue_visibility.py:1085-1160`, whose docstring line 16 states "relation lists omit related work items the caller cannot view").
- The app layer already has the same rule as `_visible_issues_q(user, prefix="")` (`app/views/workspace/user.py:68-82`) and imports it across modules (`app/views/workspace/base.py:37`).
- Scoping commits `ac0d55de3` ("scope … relation endpoints to the URL project") and `test_work_item_link_relation_project_scope.py` fixed the *URL issue* side. `create()` still says "Relations can cross projects so only workspace scope is enforced" (`relation.py:265-266`): the original authors knew relations cross projects; they never filtered what comes back.

**Should a non-guest member also be blocked from projects they aren't in? Yes.**
- VERIFIED: `_visible_issues_q` requires an active `ProjectMember` row for the issue's project at *any* role: the guest/`guest_view_all_features`/`created_by` OR-clause only decides *which issues of projects you belong to* you see (`workspace/user.py:78-82`). Search does the same (`app/views/search/issue.py:111-119`), and so does the external API (`visible_issue_q`, `api/views/issue.py:222-243`).
- VERIFIED: `ProjectEntityPermission` and `allow_permission` both refuse a user with no `ProjectMember` row in the URL project, workspace admin included (`base.py:79-92` requires "part of the project"). So the app has no "workspace admin sees everything" bypass at project level.
- INFERRED: therefore a member who isn't in B should not see B1's data through a relation either. The tests `test_member_does_not_see_related_issue_of_non_member_project` and `test_workspace_admin_gets_no_project_bypass` pin this. **These are the two places a maintainer might disagree**; see section 7.

## 4. The fix

```diff
--- a/apps/api/plane/app/views/issue/relation.py
+++ b/apps/api/plane/app/views/issue/relation.py
@@ -21,6 +21,7 @@
 from plane.app.serializers import IssueRelationSerializer, RelatedIssueSerializer
 from plane.app.permissions import ProjectEntityPermission, issue_hidden_from_guest
+from plane.app.views.workspace.user import _visible_issues_q
 from plane.db.models import (
@@ -137,8 +138,11 @@
+        # Relations can cross projects, so the related issues are limited to those the
+        # caller may view: projects they are an active member of, and for a restricted
+        # guest only the issues they created. Same rule as the external API relation list.
         queryset = (
-            Issue.issue_objects.filter(workspace__slug=slug)
+            Issue.issue_objects.filter(_visible_issues_q(request.user), workspace__slug=slug)
```

Line by line:
1. **Import.** Reuses the existing helper rather than writing a fourth copy of the rule. Importing a `_private` name from a sibling view module is already done in `workspace/base.py:37`, so it follows precedent. (Alternatives in section 7.) It imported without a circular-import error (VERIFIED: tests pass).
2. **Comment.** Matches the explanatory style of the `# SECURITY:` comments in this file.
3. **`.filter(_visible_issues_q(request.user), workspace__slug=slug)`.** `_visible_issues_q` returns `Q(project_member.member=user, is_active=True, deleted_at is null) & (Q(role > GUEST) | Q(project.guest_view_all_features=True) | Q(created_by=user))`. Passing it positionally in the *same* `filter()` as `workspace__slug` keeps all membership conditions on one join (the helper's own docstring requires this). Everything after it (annotations, `pk__in=` id lists, `.values`, the `|` unions) is unchanged. Because the filter is applied to the base queryset, it covers all eight relation types and both directions at once.

**What the filter means for each caller** (all tested): member of the related issue's project → sees it; no or inactive membership → hidden; GUEST of that project with `guest_view_all_features=False` → only issues they created; with it `True` → all of that project's issues.

**Cost.** Subquery vs pre-fetched ids? Neither was needed. VERIFIED by measurement: the endpoint runs **12 queries before and 12 after**. The rule is a `JOIN project_members` inside each of the 8 existing issue queries (1 join → 2 joins per query; the existing one comes from the active-assignee filter). A pre-fetched list of project ids would add a query and a large `IN (...)` list; a `Subquery`/`__in` on `ProjectMember` is equivalent in cost to the join. The join also reuses code the rest of the app already uses. INFERRED: `project_members` is tiny per user and indexed on `(project, member)`; I did not run `EXPLAIN` on a large dataset.

**Why not just add `.filter(project_id=project_id)`?** That would also hide legitimate cross-project relations between two projects the user belongs to. Relations are intentionally cross-project (`relation.py:266`).

**Behaviour change to be aware of:** a *restricted guest* now also stops seeing related issues in their own project that they did not create (issue detail has always refused those issues, and the external API already behaves this way: `test_external_api_guest_issue_visibility.py:1118-1125`).

## 7. Edge cases and questions for maintainers

1. **Restricted guests in their own project.** Related issues they did not create are now hidden. This matches issue detail and the external API, but changes what an existing guest sees. Intended?
2. **Workspace admins who are not members of B.** They get no bypass. Consistent with `allow_permission` and `_visible_issues_q`, but a maintainer could expect "admin sees everything".
3. **Workspace admin who is only a GUEST of a project.** `allow_permission` treats a workspace admin + project member as admin, but `issue_hidden_from_guest` and `_visible_issues_q` look only at the *project* role. UNVERIFIED how this combination behaves; pre-existing and untouched.
4. **Where should the rule live?** Options: (a) as is, importing `_visible_issues_q` from `workspace/user.py`; (b) move it to `app/permissions/` next to `issue_hidden_from_guest` and import it from both; (c) share one implementation with the external API's `visible_issue_q`. I chose (a) as the smallest change and have not refactored. Note the two existing implementations differ slightly: `_visible_issues_q` also checks `ProjectMember.deleted_at`, `visible_issue_q` does not.
5. **Other places that may disclose the same data (UNVERIFIED, not investigated):** `IssueRelationViewSet.create` returns serialized issues for any workspace issue id in the body (`relation.py:265-272`, deliberately workspace-scoped); `issue_relation.activity.*` entries in issue activity may embed the related issue's name/identifier; relation counts shown elsewhere. I kept this PR to the endpoint in the issue.
6. **`implemented_by` is not returned by `list()`** and `TIssueRelationTypes` in `packages/types` lists four keys of the eight returned. Unrelated; noted only.
7. **Soft-deleted / archived related issues** are already excluded by `issue_objects` (unchanged).
8. **Postgres 16 vs CI's 15**; Celery broker swap. Tests that don't use `.delay()` are unaffected, but treat CI as the final word.

## 10. Ten questions a reviewer might ask, with answers

1. **Why reuse `_visible_issues_q` instead of `issue_hidden_from_guest`?** `issue_hidden_from_guest` answers "may this caller see *this* issue in the *URL project*". It takes one issue and one project. Here the problem is a *set* of issues from *other* projects, so I need a queryset filter. `_visible_issues_q` is exactly that and already exists.
2. **Why not `.filter(project_id=project_id)`?** It would also hide valid relations between two projects the user is in. `create()` explicitly allows cross-project relations (`relation.py:265-266`).
3. **Is this only a guest problem?** No. A member or workspace admin of A who is not in B got B1 too (my tests fail on base code for both). The title says guest; the missing check is project membership.
4. **Why do restricted guests now lose some related issues in their own project?** Issue detail already returns 403 for issues a restricted guest didn't create, and the external API's relation list filters the same way. Showing the name in a relation list while refusing the issue page would be inconsistent. I flagged it as a question.
5. **Does it add queries?** No: 12 before, 12 after for the same data (measured). One extra `JOIN project_members` in each of the 8 existing issue queries.
6. **Why a join instead of a subquery or a pre-fetched list of project ids?** The helper expresses the rule as a join and the rest of the app does it that way. A prefetched list costs one more query and a long `IN`; a subquery gives no benefit here. I did not benchmark on a large dataset.
7. **Why import a private (`_`) function across modules?** `workspace/base.py:37` already does. Moving it to `app/permissions/` would be cleaner, but is a refactor outside a minimal bug fix; I listed it as an option for maintainers.
8. **Does the frontend need changes?** No. `fetchRelations` stores whatever IDs come back and `RelationIssueList` renders those IDs (read, not run in a browser).
9. **How do you know the tests test the bug?** They fail on unmodified `preview` (16 failures, with the B1 id visible in the assertion output) and pass with the change. I also fixed two assertion bugs of my own that would have let them pass vacuously (UUID vs `str`, lazy queryset vs list).
10. **What did you not test?** A running stack (no Docker here); Postgres 15 (I used 16); other endpoints that might expose related-issue data (activity, relation `create` response); the workspace-admin-who-is-a-project-guest combination. The 91/17/16 failures in my full runs were environment (no RabbitMQ, no `EMAIL_HOST`) and were identical before and after; the final run with both set (0 failures before and after) is in section 6.
